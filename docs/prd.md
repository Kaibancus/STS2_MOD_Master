# STS2 新角色 MOD 产品需求文档

状态：已批准的文档基线。工程范围和验收门已确定，角色创作输入待用户提供。

## 1. 产品目标与交付边界

为拥有《Slay the Spire 2》的玩家新增一个可游玩的单人角色，
使其能够通过正常角色选择进入游戏，使用专属卡牌、遗物及用户设计的核心机制，
完成游戏原生支持的流程和存档续玩。

“可以加载 DLL”“能显示角色按钮”“能打一场战斗”分别只是工程里程碑，
不能单独代表完整角色 MOD 已完成。

本项目同时建立可持续维护的工程文档：实施计划、任务看板、BUG/FIX 看板和工程日志。
每个交付结论必须能追溯到需求、任务、实现提交和验证记录。

本次文档建设不等于开始角色业务实现。角色设定、数值和内容量未确定前，
只允许经单独批准的工具准备与技术探针，不得将占位验证内容冒充正式设计。

## 2. 已确认范围

| 范围 | 首期策略 |
| --- | --- |
| 角色数量 | 一个新增角色，不替换原版角色 |
| 游戏模式 | 单人游戏 |
| 核心功能 | 角色选择、专属卡牌/遗物、核心机制、战斗表现、存档兼容 |
| 工程文档 | 仓库内中文 Markdown，随实现持续维护 |
| 创作设计 | 由用户填写 `character-design.md`；初始文件必须为零字节 |
| 联机 | 后续范围；首期不承诺联机兼容 |
| 创意工坊 | 后续范围；首期以本地安装包交付 |
| 原版内容 | 不修改原安装，不分发游戏本体或提取资产 |
| 工具隔离 | 如需 Godot，安装到工作区的 `Godot` 目录，不进入 Git |

首期不默认增加新职业系统、地图、怪物、事件、药水、多人规则、在线服务、
遥测、自动更新器或第三方 MOD 管理平台。这些能力只有在后续范围变更获批后进入计划。

## 3. 目标用户与主要流程

玩家：安装与当前游戏版本匹配的 MOD 和明确列出的依赖，启用后选择新角色，
理解卡牌与机制，进行单人游戏，在受支持的存档边界退出和续玩。

角色设计者：在专属设计文档中提供设定、规则、内容清单和资源要求；
通过带版本的设计基线评审和试玩反馈调整内容。

实现者：从锁定的版本和需求出发工作，更新任务状态，记录实现证据、
已知问题及修复过程，不以聊天记录代替工程日志。

维护者：识别游戏更新造成的兼容变化，执行回归，发布带兼容说明的新版本，
保持普通玩家数据与测试数据隔离。

## 4. 尚待用户提供的创作输入

以下内容不由本 PRD 代填，也不预先写入空白角色设计文件。

| 输入 | 影响的工程工作 | 决策门 |
| --- | --- | --- |
| 角色名称、身份、主题和视觉方向 | 资源命名、本地化、人物展示 | 正式内容实现前 |
| 核心机制及完整规则 | 状态模型、钩子、UI、保存策略 | 机制实现前 |
| 初始属性、牌组和遗物 | 角色模型和初始化逻辑 | 可玩垂直切片前 |
| 卡牌、遗物清单及各项数值 | 内容规模、池、升级、平衡 | 对应内容批次前 |
| 解锁策略 | 角色选择、解锁池和进度处理 | 端到端流程验收前 |
| 发布语言 | 本地化表、字体和排版验证 | 文案集成前 |
| 美术、动画和音频形式及来源 | 工具、许可证、资源适配 | 资源管线冻结前 |
| 对现有 MOD 的兼容承诺 | 依赖和冲突回归矩阵 | 测试范围冻结前 |

“未定”不是允许实现者自行设定。工程计划应显式阻塞依赖这些输入的任务，
同时允许与设计无关的静态检查、工具准备和受控技术探针继续。

## 5. 功能需求

| ID | 需求 | 完成定义 |
| --- | --- | --- |
| FR-01 | 正确装载与身份 | 使用稳定且唯一的 MOD ID；Manifest 与产物一致；版本、作者、玩法影响标记和依赖声明准确；不能加载时给出可定位的错误，而非伪装成功。 |
| FR-02 | 新增角色选择 | 新角色可出现在正确的选择入口；名称、说明、图标、锁定/解锁状态与用户设计一致；不覆盖原版角色的 ID、文本或资源。 |
| FR-03 | 初始化角色状态 | 初始血量、金币、能量、牌组、遗物等来自获批设计；模型实例和所属玩家正确，不修改共享 canonical 模板。 |
| FR-04 | 正常内容获取 | 专属内容按设计进入合法角色池、奖励、商店和图鉴；正确处理稀有度、解锁和排除条件；不把全量数据库当作奖励池。 |
| FR-05 | 卡牌行为 | 费用、目标、可用条件、效果、升级和设计涉及的保留/消耗/重复结算等规则一致；文本预览与实际结果相符；走正确命令及生命周期。 |
| FR-06 | 核心机制 | 机制状态的所有者、作用域、变化触发、清理和必要保存边界都有明确规则；不存在重复订阅、无限触发或跨战斗/跨局串扰。 |
| FR-07 | 遗物行为 | 初始及后续专属遗物按设计生效，获取/移除、回合、战斗和房间生命周期正确；没有失效后残留的效果或订阅。 |
| FR-08 | 文本与提示 | 覆盖目标语言中的角色、卡牌、遗物、状态、提示和必要错误说明；动态变量、费用变化、升级和目标预览可正确展示。 |
| FR-09 | 资源与表现 | 角色选择、战斗、地图及设计涉及的休息点/商店/事件界面使用完整资源映射；表现与逻辑分离，缺失必要资源不会静默进入破损流程。 |
| FR-10 | 受支持的保存/续玩 | 在游戏本版本原生支持的保存边界往返后，角色、牌组、遗物和需持久化的机制状态一致；不承诺未经确认的任意战斗中断点续玩。 |
| FR-11 | 兼容性失败处理 | 依赖缺失、版本不匹配、模型 ID 不可解析或不支持的旧档有明确限制说明和安全处理；不承诺卸载 MOD 后仍能继续含其内容的存档。 |
| FR-12 | 原版非回归 | 不启用此 MOD 时保持原版行为；启用时不无意改变原版角色、公共池和全局规则；所有有意影响必须列入设计和回归范围。 |
| FR-13 | 安装与移除说明 | 提供最小安装文件清单、依赖、兼容版本、启用步骤、日志定位和安全移除警告；不要求下载或复制受限游戏文件。 |
| FR-14 | 工程可追溯 | 每项实施有任务 ID、验收和证据；每个确认缺陷有独立 ID、复现、修复提交及复验；工程日志记录真实发生的工作和偏差。 |

FR-09 的资源覆盖不能直接等同于“需要制作所有原版同类动画”。
资源矩阵应逐项标记必需、自有替代方案、确认可复用的引用、或不适用，
并保留适配证据；不得把提取原版素材作为默认公开交付策略。

## 6. 非功能需求

| ID | 要求 | 验收原则 |
| --- | --- | --- |
| NFR-01 | 玩家数据安全 | 测试存储和云端行为先隔离再启动；备份不代替隔离；自动化不得写入或恢复真实档位。 |
| NFR-02 | 可重复性 | 锁定游戏、SDK、Godot、库与工具基线；可重建自身产物；不在远端携带游戏依赖。 |
| NFR-03 | 确定性 | 相同种子、输入序列、版本和依赖组合下，受测玩法状态一致；视觉随机不污染玩法随机。 |
| NFR-04 | 稳定性 | 获批回归矩阵中不出现未处理异常、卡死、重复触发、损坏存档或必要资源缺失；失败用例不能标记通过。 |
| NFR-05 | 性能与资源生命周期 | 建立指定场景的加载、帧表现和资源生命周期基线；性能预算在测得基线后冻结，不虚构尚未测量的毫秒或内存目标。 |
| NFR-06 | 可维护性 | 原生扩展点优先，兼容适配集中；Harmony 补丁有目标版本、必要性、风险和回归用例。 |
| NFR-07 | 可观测性与隐私 | 日志可关联版本、MOD、任务和异常上下文；公开日志先脱敏；默认无遥测、联网和用户数据上传。 |
| NFR-08 | 授权与发布边界 | 只分发自身或有明确授权的代码/资产；第三方许可和来源可追溯；游戏本体、原版代码/资产、存档和本机信息不进入历史或安装包。 |

## 7. 体验和兼容测试维度

至少覆盖启动/启用/禁用、角色选择、开局状态、战斗基本循环、
获批机制边界、卡牌升级和变形等实际涉及的交互、奖励与商店、
房间切换、正常胜败和退出、受支持的保存/续玩、缺依赖及坏资源提示。

还需覆盖键鼠与游戏本身支持且项目声明支持的输入方式、长文本和目标语言排版、
界面缩放、各种目标选择条件以及资源场景切换。
具体测试组合由设计覆盖矩阵决定，不承诺未经规划的所有外部 MOD 组合。

独立列出不支持项：首期联机、创意工坊发布、未列入兼容表的游戏版本、
未证实支持的热重载、未经确认的旧版 MOD 存档迁移。

## 8. 验收门

| 门 | 目的 | 退出条件 |
| --- | --- | --- |
| G0 文档与来源 | 防止在错误版本或无依据教程上开工 | 基线、来源、需求、待定输入和任务依赖清楚；设计文件仍由用户独占填写。 |
| G1 数据隔离 | 保护真实玩家数据 | 开发写入位置与云行为有证据；方案不触及原安装/真实档位；未通过时禁止游戏级探针。 |
| G2 装载与接口 | 排除工具和 ABI 假设 | 最小自身 MOD 在固定环境装载；Manifest、注册时机和资源入口得到验证；仅保留必要依赖。 |
| G3 设计冻结与垂直切片 | 确认业务实现起点 | 用户提供当前阶段设计；选择角色、开局、机制代表行为、正常结束和支持的续玩形成闭环。 |
| G4 内容完整与回归 | 防止演示冒充正式内容 | 获批清单逐项完成，资源/本地化/池/测试矩阵覆盖；阻断缺陷关闭。 |
| G5 发布 | 保证可安装且不越界 | 干净安装、兼容说明、自身产物清单、授权和历史审查、已知限制完整；提供可定位版本。 |

G2 的技术探针使用可丢弃的工程占位，不决定正式角色的创意或内容配额。
任何门未通过均记录原因与后续任务，不能以默认值或忽略错误绕过。

## 9. 需求变更与文档权威

- 用户维护的角色设计是创作来源；PRD 管理产品边界和验收，不复制另一套冲突设定。
- 实施计划管理阶段和依赖，任务看板管理当前执行状态，BUG/FIX 看板管理已确认缺陷，
  工程日志保存发生过的事实；风险与缺陷必须分开。
- 变更需说明涉及哪些 FR/NFR、设计版本、实现任务、存档及兼容影响。
- 关闭任务时附实际证据；未执行的验证明确写“未执行”，不能写成成功。
- 本 PRD 不提供工期估算，也不提前填入未决定的角色数值、卡牌数量或资产预算。
