# 工程实施计划

状态：批准文档基线已发布，候选编辑器准备已完成；交付证据见 D-05 与工程日志。
后续安全探针和角色实现尚未开始。

本计划引用 [PRD](prd.md) 的 FR/NFR 与 G0-G5 验收门。
工具版本、来源和风险以技术评估文档为准；当前状态以任务看板为准。
本计划不提供工期估算，不把尚未确定的角色内容写成实施事实。

## 1. 阶段关系

文档与工具准备之后，先建立测试数据隔离，再进行本版本装载和接口探针。
接口探针与用户编写角色设计可以独立推进；正式业务实现依赖两者。

最小可玩闭环形成后，按设计逐批集成内容、表现和本地化，再进行完整回归与本地发布。
联机和创意工坊不在首期执行路径中。

`P0 -> P1 -> P2 -> P3 -> P4 -> P5`

其中 P3 还依赖用户提供角色设计；P0 的文档交付不依赖用户立即完成创作。

## 3. P0：工程基线与文档治理

前置：确认源目录、Git 边界、版本指纹与资料来源。

工作：

- 固化当前 `v0.111.0`、GodotSharp `4.5.1`、`net9.0`、Harmony `2.4.2` 基线；
  记录本机工具版本与游戏随附运行时的区别。
- 引用 DLL 只通过本机路径定位，不复制到可发布的源码或产物中。
- 建立未来 `global.json`、依赖版本和锁文件的决策点；
  当前文档阶段不无故创建空的工程或安装包。
- 编写各类工程文档及索引。角色设计保持空白，后续不得由代理擅自填充。
- 建立文档更新规则与来源检查规则，区分已证实事实、推断、待验证假设。

输出：当前文档包、版本/环境清单、首批技术风险和待定决策、必要时的隔离编辑器。

退出：G0。代码仓库只包含可公开自身文件；工具、提取内容和真实数据均在外部。

## 4. P1：开发安全边界

前置：P0；尚不要求用户完成角色设计。

工作：

- 确认本版本 `UserDataPathProvider`、`SaveManager.ConstructDefault`、
  本地/云存储组合及初始化顺序；必要时做仅本地的方法级分析。
- 比较经证实的专用保存路径配置、独立测试系统身份/环境等方案；
  不把未确认的通用 Godot 参数当成隔离实现。
- 同时覆盖 profile、settings、进度、运行历史和云端键/后端；
  仅换档位或看到 `modded` 目录不能通过。
- 设计启动前检查：目标必须为游戏副本；测试存储必须指向批准的可丢弃目录；
  无法确认时拒绝启动并记录原因。
- 日志和开发测试文件保持本地，公开证据先脱敏。
- 不备份、迁移或修改现有其他 MOD 的真实存档。后续本 MOD 自建测试夹具
  与本机玩家数据严格区分。

输出：隔离方案的决策记录、可说明的读写边界及验证步骤。

退出：G1。未通过时禁止所有需要启动游戏的后续探针。
如需要新增系统账户、虚拟环境、云设置调整或额外权限，应单独请求确认，
不将这些系统变更藏在普通开发脚本里。

## 5. P2：接口与工具的最小技术探针

前置：P1；仅使用可丢弃工程占位，不确定正式角色设定。

| 任务 | 验证问题 | 必须留下的证据 |
| --- | --- | --- |
| 装载探针 | 原生入口、Manifest、`min_game_version` 与依赖声明是否适配本版 | 自身 DLL/Manifest 清单、装载日志、明确的失败用例 |
| 模型探针 | 原生发现/注册何时完成，稳定 ID 是否正确 | 入口与数据库顺序、重复 ID 和迟注册的结果 |
| 池探针 | 合法池、解锁和普通奖励是否一致 | 不使用全量模型库抽奖；奖励/商店/图鉴观察 |
| 角色资源探针 | 非 virtual 视觉路径和必要界面能否接入 | 原生路径、最小适配和候选库的对比证据 |
| 资源包探针 | 自有资源导入、UID/路径、PCK 装载是否成立 | 从干净本地环境生成的自身资源包，不依赖游戏导出工程 |
| 命令/钩子探针 | 核心命令的异步顺序、监听范围、退出清理 | 代表动作序列、无重复结算与无遗留订阅证据 |
| 存档探针 | 注解类型限制、恢复时机、模型/字段变更处理 | 原生支持边界内的往返、缺模型/旧版本等受控负面用例 |
| 随机数探针 | 流选择和重放/续玩是否一致 | 固定版本、种子和输入序列下的状态比较 |

本版本已有原生 `ModHelper` 和 `ModelDb` 扩展点，不能直接采用早期教程的全面补丁方案。
另一方面，`CharacterModel` 部分资源入口不可直接 override，
也不能未经验证宣称“只继承角色类即可完成接入”。

技术选择遵循最小必要依赖原则：原生入口优先，候选社区库仅用于已确认的缺口；
确定版本与许可证后才纳入依赖。补丁集中在适配层，不扩散到每张卡牌。

退出：G2；确定实际可工作的最小工具链、依赖和适配范围。
探针失败创建任务或经确认的缺陷，不以吞异常、默认成功或写原版文件绕过。

## 6. P3：设计基线与可玩垂直切片

前置：G2；用户为该阶段提供可实施的角色设计，并明确发布语言与解锁策略。

设计检查不是代写：检查规则是否定义作用域、时序、上限/边界、资源变化、
升级差异和保存需求；把歧义交回用户决定。

推荐职责划分：

| 组件 | 职责 | 禁止混入 |
| --- | --- | --- |
| Bootstrap / 兼容适配 | 入口、版本检查、必要注册和局部兼容处理 | 每张卡牌的具体玩法 |
| Character / Pools | 角色元信息、初始状态、合法内容池 | 直接修改原版全局数据 |
| Cards / Relics / Powers | 按设计实现内容模型及生命周期 | 文件系统、任意网络和资源包装载 |
| Mechanic 状态层 | 明确范围的机制状态与规则 | UI 节点存储核心状态、隐式静态跨局状态 |
| Presentation | 角色场景、UI、VFX、声音和显示适配 | 在入队表现回调中进行玩法结算 |
| Localization | 文本表、动态变量、目标语言显示 | 与实际结算相矛盾的重复常量 |
| Serialization 适配 | 保存的最小状态、恢复和版本策略 | 把整个 UI 或运行时对象图序列化 |

实现顺序：

1. 确定 MOD/模型/资源命名空间及稳定 ID，不随显示名称变化而改 ID。
2. 完成角色选择与正确初始化，满足角色类型契约。
3. 实现用户设计中的一个端到端机制路径和代表性内容，覆盖真实生命周期。
4. 接入对应显示、本地化和资源，而不是用 UI 回调代替机制状态。
5. 完成战斗结束、房间切换和原生支持的保存/续玩闭环。

退出：G3。代表性内容只是垂直切片；最终卡牌和遗物数量仍由用户设计清单决定。

## 7. P4：内容、资源与回归矩阵

前置：G3；每一批新增内容有已批准设计和验收用例。

- 以设计清单为单位扩展卡牌、遗物、状态及必要资源；每项关联 FR 和任务 ID。
- 同步测试获得方式、费用/目标边界、升级、叠加、触发顺序和结束清理。
- 针对正式涉及的抽牌、复制、变形、生成、保留、消耗及增减费组合建立交互矩阵；
  不将没有涉及的机制虚构成已支持。
- 覆盖角色选择、战斗、地图、休息点、商店和事件等实际用到的资源入口。
- 对每个资源记录原创/授权来源和所需署名；不公开提取游戏资源。
- 覆盖所有声明支持语言的动态文本、长文本、提示、费用和升级预览。
- 测试普通角色与共享内容池，检查全局补丁影响。
- 测试保存往返、重复开局、正常关闭、错误依赖及坏资源。
- 使用指定观察场景建立性能和内存生命周期记录，再冻结性能预算。
- 对外部 MOD 只承诺实际列入兼容矩阵的组合。

退出：G4；阻断缺陷已关闭且有复验，未解决限制公开列出。
风险不是缺陷；复现失败也不是已修复。

## 8. P5：最小本地发布与后续维护

前置：G4。

- 使用独立打包步骤列举允许进入安装包的自身 DLL、PCK、Manifest 和必要文档。
- 编译引用以外部游戏 DLL 解析，防止 CopyLocal/发布步骤把游戏程序集带入包中。
- 分开管理仓库源文件、忽略的构建产物和实际分发包；
  `.gitignore` 不能代替对分发包与 Git 历史的审查。
- 在批准的隔离环境执行干净安装、启用、禁用和错误依赖流程。
- 记录兼容游戏版本、依赖版本、构建标识、已知限制及存档警告。
- 完成工程日志、任务和 BUG/FIX 状态，保留实际提交与验证证据。
- 不自动创建创意工坊条目、不安装外部 MOD 管理器、不引入自动更新和遥测。

退出：G5。首期交付本地可安装角色 MOD，联机和创意工坊另行立项。

游戏升级后的维护流程：冻结旧基线与已知可用自身产物，采集新版本指纹，
比较装载/角色资源/存档等关键接口，重跑门禁和回归，再声明新版本兼容。
不通过自动追随“最新版”修改当前工作环境。

## 9. 工程记录规则

| 文档 | 管理内容 | 更新要求 |
| --- | --- | --- |
| 实施计划 | 阶段、前置条件、范围和验收门 | 范围/架构/依赖改变时更新，保留变更理由 |
| 任务看板 | 当前任务状态和证据 | 开始工作先标进行中；结束时链接实际输出和提交 |
| BUG/FIX 看板 | 已确认缺陷及修复闭环 | 有复现才登记；修复与复验分开记录 |
| 工程日志 | 发生过的事实与偏差 | 每次实施批次追加；不回写伪造过去的成功 |
| 角色设计文档 | 用户创作输入 | 初始为空；未经用户要求不补写设定或模板 |

任务状态采用：待办、就绪、进行中、阻塞、待验收、完成。
缺陷状态采用：待确认、已确认、修复中、待复验、已关闭、重新打开。
只有待确认且具备真实问题线索的记录才进入缺陷看板，纯技术假设保留在风险清单。

关闭证据应能说明执行了什么、使用哪个版本、结果是什么及有什么未覆盖；
不能只填写“测试通过”。文档变更可用链接、结构和状态一致性检查，
不为文档仓库无故引入新的测试/构建依赖。
